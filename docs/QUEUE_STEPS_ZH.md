# 单 link 队列模型:每一步做了什么,以及方案哪里不对

四条走廊(I-395 NB/SB、I-66 EB/WB),**252 条 TAPLite link**,来自 154 个 TMC。
速度是 2025 年 10 月 **23 个工作日**的平均,15 分钟一格。

所有输入来自 `link-queue-simulation` 共享包。

代码:`scripts/queue_step*.py`,输出:`outputs/nvta_queue/`。

---

## 总览:方案有 6 处和实际不符

| 方案说 | 实际 | 严重程度 |
|---|---|---|
| μ 可以从数据测出来 | **测不出来。μ_free 恒等于输入的 capacity** | 大 |
| 逐点 `dQ/dt` 会被噪声淹没 | 只噪 1.3 倍,不是 12 倍 | 中 |
| B-spline 是为了抑制噪声 | 真正作用是让拟合**可能失败** | 中 |
| 多个 TMC 合成一条 link | 反过来,一个 TMC 对多条 link | 中 |
| V_assign 冲突原因有 3 类 | 漏了**下游回溢** | 中 |
| 速度是 5 分钟单日 | 15 分钟 23 天 | 小(是好事) |

外加一条方案没提、但结果最重要的:

> **assignment 的流量只有容量的 45%,单靠它永远产生不了拥堵。模型全部的拟合能力来自速度数据,而速度数据在第 4 步已经被拟合过。**

## 第 0 步:输入

| 方案要的 | 共享包里 |
|---|---|
| `v(t)` 观测速度 | `tmc-15min-speed/<走廊>/Readings.csv` |
| `V_assign` | `TAPLite-.../{am,md,pm}/link_performance.csv` 的 `volume` |
| lanes / L / capacity / v_f | 同上 |
| QVDF 参数 | 同上的 `P/t0/t2/t3/vt2_mph/mu` |
| OD matrix | **没有**(只影响第 5 步的硬上界) |

连接键:`tmc-matching/canonical_node_pair_tmc-1v1.csv`。

### 偏差 1:聚合方向反了

方案假设"多个 TMC 在一条 link 上",要做长度加权调和平均。实际相反:

| 一个 TMC 带几条 link | TMC 数 |
|---:|---:|
| 1 | 72 |
| 2 | 31 |
| 3–6 | 27 |
| 10 | 2 |

所以速度是**广播**下去的,不用平均。

**但代价是:252 条 link 只有 132 个独立观测。** 同一 TMC 下的 link 速度、cutoff、episode 完全相同。汇报样本量时必须按 TMC 去重 —— 说"76 条 link 有拥堵"听起来比证据多,真实是 44 个 TMC。

### 偏差 2:15 分钟 × 23 天,不是 5 分钟 × 5 天

| | 5 天 | 23 天 |
|---|---:|---:|
| 单个 bin 均值标准误 | 0.900 mph | **0.502 mph** |

假日(10/13)查过了,剔掉只动 0.155 mph,不值得加特判。**这是好事,但它让第 4 步的一个论证失效了**(见后)。

## 关键前置:free flow speed

这个值决定 cutoff,cutoff 决定哪些 bin 算拥堵,进而决定 D、episode、队列。方案自己写它 "dominates everything"。

**六种口径,自己从 TMC 原始数据算的(中位数,mph):**

| 走廊 | TMC | **每TMC p95**<br>(采用) | 整走廊 p95 | 夜间中位 | 全时段最高 | INRIX reference | assignment |
|---|---:|---:|---:|---:|---:|---:|---:|
| I-395 NB | 21 | **65.62** | 65.89 | 61.92 | 69.59 | 59.0 | 63.0 |
| I-395 SB | 20 | **63.18** | 64.77 | 59.57 | 68.50 | 59.5 | 63.0 |
| I-66 EB | 57 | **67.86** | 71.00 | 63.60 | 71.48 | 64.0 | **75.0** |
| I-66 WB | 56 | **67.88** | 70.93 | 64.52 | 72.00 | 64.0 | **75.0** |

**硬判据:自由流速度不可能高过这条路跑出过的最高速。**

| | 超过实测最高速的 TMC |
|---|---:|
| assignment 的 `free_speed_mph` | **72 / 154(47%)** |
| 我们的 per-TMC p95 | 0 |

I-66 WB 全部 109 条 link 被赋 75 mph,而其中 link 26304 全天最高才 **55.00 mph**。

**为什么不用走廊级 p95:** 走廊内部各段 p95 差 16–22 mph。I-66 EB 走廊值 71.0 就是最快那几段的水平;套到自身 p95 只有 54.3 的路段上,cutoff 差 11.7 mph,那段会被判成常年拥堵。

**可信度:** 我们的 p95 和另外两条独立路径高度一致 —— INRIX 自己的 `reference_speed` 相关 **0.963**,夜间实测相关 **0.979**,只差一个约 3.7 mph 的常数偏移。分位数换成 p85 或 p99,cutoff 只移动 1.7–3.8 mph。

**换成这个值之后,12 个"全天拥堵"的异常 episode 自动消失 9 个,不需要任何过滤规则。**

## 第 1 步:速度转流量

$$q(t)=S_3\big(v(t)\big),\qquad m=4$$

**正确性检验** —— q/C 随 v/v_f 的走向:

| v / v_f | q/C 中位 |
|---|---:|
| 0.30–0.50 | 0.877 |
| 0.50–0.65 | 0.977 |
| **0.65–0.72** | **0.999** |
| 0.72–0.85 | 0.975 |
| 0.85–1.10 | **0.826** |

峰值恰好落在 `v/v_f = 0.707 = 2^(-1/2)`,`max q/C = 1.0000`。实现正确。

**要记住最后一行:** 一条以自由流速度跑的 link,S3 说它载着 **83% 的容量**。这不是测量,是 S3 在高速段的固定返回值。PM 期只有 **20.3%** 的 bin 在 cutoff 以下,其余 80% 的 q 都不可信。

参数换成真值:lane capacity **2000 vphpl**(原假设 2200),free speed 每 link 一个。

## 第 2 步:服务率 μ

方案要求两个状态:自由流用"崩溃前 q 峰值",拥堵用"episode 内 q 中位数"。

### 偏差 3(最严重):μ_free 测不出来

用同一个估计器,换五个假设 capacity:

| 假设 C | μ_free / C |
|---:|---:|
| 1800 | 0.9979 |
| 2000 | 0.9979 |
| 2200 | 0.9979 |
| 2400 | 0.9979 |

**μ_free 严格等于 C × 0.998,零信息。**

原因是恒等式,不是估计误差:

- S3 的 `q(v)` 在 `v = v_f/√2 = 0.707·v_f` 处**恰好等于 C**
- 我们的 cutoff 是 `0.70·v_f`
- **两个几乎是同一个点** —— "崩溃前"这个窗口必然扫过它,必然取到 C

真实 link 25947 的实际数据(v_f=63.0,C=1900):

| 时刻 | 速度 | v/v_f | q@C=1800 | q@C=2000 | q@C=2200 |
|---|---:|---:|---:|---:|---:|
| 16:15 | 44.67 | 0.709 | **1800.0** | **2000.0** | **2200.0** |

**所以方案第 2 步末尾那句 "Nothing above is assumed; every value is read from the data" 是错的。** `configs/nvta_mu_prior.json` 原来写的 *"mu is an assumption, not a measurement"* 才是对的。

**这不是说值错了。** capacity 的定义就是最大流出率,μ_free 就该等于 C。只是它是**输入不是测量**。既然结果注定是 C,就直接读 `link_capacity`,省掉一堆检测代码。

### 偏差 4:按天估计没用

方案强调 `max(mean) ≤ mean(max)`,要求逐天估计峰值再取中位数。实测:

| | μ_free / capacity |
|---|---:|
| 先平均剖面再取峰 | 0.9985 |
| 逐天取峰再取中位 | 0.9933 |

差 **0.30%,方向还相反**。这套机器可以删掉。

### 能测的只有比值

`1 − μ_queued/μ_free` 里 C 上下约掉(C=1900 和 C=2200 算出来差 3.3e-16):

| | 中位 | IQR |
|---|---:|---:|
| **capacity drop** | **6.83%** | 3.71–10.90% |
| config 原假设 | 10% | |

但这个 drop 也**不是真正的测量** —— 文献里 capacity drop 是拿检测器计数测的,前后两个流量各自独立观测;这里两个都是同一条速度曲线过同一个 S3 映射出来的。

### 方案的 AM/PM 问题:答不了

| | n | drop 中位 |
|---|---:|---:|
| AM | 34 | 3.99% |
| PM | 47 | 8.67% |

Mann-Whitney p = 0.030,看着"显著不同"。**但 AM 拥堵的 link 和 PM 拥堵的 link 基本是两批不同的 link**,这个差异混着"哪些 link 会堵"的成分。

同时有 AM 和 PM episode 的只有 **7 条**,在这 7 条上 **PM − AM = −2.13 个百分点,方向反了**。

结论:**用现有数据答不了。** 好在我们每个 episode 各存一个 μ_queued,不需要按时段合并。

### 异常 episode 的处理

12 个超 8 小时的 episode,**不能按时长删**:时长和深度相关性只有 0.22,最长的几条是 I-395 NB 速度掉到 9.4 mph 的真拥堵,是全网最堵的证据。

改用**深度门槛**(v_T2 ≤ 0.85 × cutoff),滤掉 14 个又短又浅的。

最终:**87 个 episode,76 条 link**(PM 47 / AM 34 / MD 6 / NT 0),capacity_drop 无负值。

### 一条记下来没处理的

不看阈值找崩溃点(PM 爬升段单 bin 降幅最大处),落在 **0.82·v_f**,不是 0.707。**72% 的 link 在 S3 的 capacity 速度以上就崩了**,中位差 10.6 mph。反推 m 应该是 7 不是 4。第 3 步查过影响,很小(见下),没动。

## 第 3 步:速度隐含队列

$$Q_{\text{meas}}(t)=\mu(t)\left(\frac{L}{v(t)}-\frac{L}{v_f}\right)$$

单位:`L/v` 小时 × `μ` 辆/小时 = **辆**。用**未平滑**速度 —— 平滑过的已经用来定 episode 和 μ,再用一次等于把同一次平滑洗两遍。

| | |
|---|---|
| 有队列的 link | 76 条(44 个独立 TMC) |
| 峰值队列 | 中位 46 辆,IQR 29–78,最大 326 |
| **存储量检验** | **0 个 bin 超标**,最差 0.74 |

### episode 边界的疑问:结案

第 2 步那个"崩溃在 0.82 而 cutoff 在 0.70,边界是不是切掉真队列"的问题:

| | |
|---|---:|
| episode 外被清零的量 | 54.5%(**统计假象**) |
| 每 bin:内 vs 外 | 43.5 辆 vs **3.11 辆** |
| bin 数量比 | 外:内 = 16.7 : 1 |
| 其中在**从不拥堵**的 link 上 | 65% |
| **真正被切掉的,相对捕获量** | **6.5%** |

那 3.11 辆/bin 是**口径的地板**:v_f 取 p95,95% 的 bin 速度都略低于它,`L/v − L/v_f` 永远是小正数。不是队列。

**结论:cutoff 偏保守,代价 6.5%,不值得改。**

## 第 4 步:到达率 λ

$$\lambda=\mu+\frac{dQ}{dt}$$

不逐点用,改成 **27 个 B-spline 系数**(60 分钟节点)对 96 个 bin,用最小二乘拟合 `Q_fitted − Q_meas`。

### 偏差 5:方案给的理由不成立

方案说逐点差分会被噪声淹没。实测(前向差分,和递推严格对应):

| | 逐点 | B-spline |
|---|---:|---:|
| bin 间跳动 SD | 23 vph | 17 vph |
| 占 μ 比例 | 0.33% | 0.25% |
| 负到达率的 link | **0 / 76** | 0 |

**只噪 1.3 倍,不是 12 倍。** 因为我们的数据比方案假设的干净约 6 倍(15 分钟 bin 差分放大小 3 倍 × 23 天平均噪声小 2.1 倍)。

### 真正的理由:参数比数据少,拟合才可能失败

两个实验:

**实验 1** —— 逐点 λ(96 个自由值)喂进递推:

```
残差 RMSE = 0.000 辆 = 峰值的 0.000%
```

**完美复现。96 个 bin、96 个未知数,方程组恰定,残差必为零,模型不可证伪。**

**实验 2** —— 节点间距扫描:

| 节点 | 系数 | bin/系数 | RMSE | 占峰值 |
|---:|---:|---:|---:|---:|
| 15 分钟 | 99 | 0.97 | — | 求解器拒绝(参数>数据) |
| 20 分钟 | 75 | 1.3 | 2.88 | 2.2% |
| **60 分钟** | **27** | **3.6** | 5.50 | **4.1%** |
| 480 分钟 | 6 | 16.0 | 10.94 | 8.5% |

**可证伪性是买来的,代价就是那 4.1% 的残差。** 想让残差好看只要把节点调密,但那时第 8 步的验证就失效了。

### 结果

| | |
|---|---|
| 拟合的 link | 76 条 |
| 队列残差 | RMSE 2.0 辆中位,占峰值 **4.1%** |
| 拟合峰/实测峰 | 0.968 |
| 相关性 | **0.9842**(逐 link 中位 0.944) |
| λ 无负值、队列无负值、**所有 link 当天清零** | ✓ |

物理正确:λ 在 μ 上方时队列涨,下方时队列落。双峰 link 两个峰都跟上了。

### 结构性结果

**λ 只在 5.6% 的 bin 上可识别。** 其余 94.4% 是自由流,那里 `Q ≡ 0` 对**任何** λ < μ 都成立(800、1500、1999 给出完全相同的队列和速度)。这些 bin 不是"估不准",是**数学上没有唯一解**,全部交给第 5 步。

## 第 5 步:总量锚定

$$\sum_t \lambda(t)\,\Delta t = V_{\text{assign}}(\text{period})$$

**单位先验证过**(这个项目早先在 D/C 单位上栽过一次):`D = volume/(lanes × 周期小时 × plf)` 在 **100% 的行**上成立,误差 <0.1%。所以 `volume` 是**周期总车辆数(全车道)**。

跑 AM、MD、PM 三个周期,因为第 6 步是一条连续递推,15:00 时已有的队列必须带进来。

### φ 在这里,但作用域缩小了

早期方案是 `λ(t)Δt = V_assign × φ(t)`,φ 是整个周期归一化的 q 形状。

**问题:拥堵时 q 是 throughput 不是 demand。** 堵得最狠那一刻需求最高,但 FD 反推出的流量最低 —— 整个周期用 φ 会**把需求高峰压成凹坑,形状是反的**。

所以现在:

| bin 类型 | λ 从哪来 |
|---|---|
| queued(5.6%) | 第 4 步队列拟合 |
| free-flow(94.4%) | **φ,只在自由流 bin 上归一化** |

实测 φ 在自由流段几乎是平的(0.097–0.102),因为 S3 在高速时对速度不敏感。**所以 φ 其实没带来多少形状信息,基本等于均分。**

### 上下界(都不来自 assignment)

- **下界** = Σ(queued bin 的 q·Δt) —— 已经看到疏散掉的量
- **上界** = 下界 + Σ(free bin 的 μ_free·Δt) —— 自由流 bin 能装下的极限

### 主要发现:高峰期对不上

| 周期 | link | 窗口内 | 有队列的 | 其中窗口内 | **其中低于下界** |
|---|---:|---:|---:|---:|---:|
| AM | 252 | 226 | 37 | 13 | **22** |
| MD | 252 | 239 | 49 | **36** | 12 |
| PM | 252 | 213 | 53 | 15 | **34** |

**平峰基本吻合,早晚高峰对不上。**

那 34 条(PM)的具体情况:

| | 中位 |
|---|---:|
| assignment 给的量 | **903 vph/车道** |
| 占容量比例 | **45%** |
| 速度数据显示的排队时长 | **4.00 小时** |
| 排队期间释放率 | 1,677 vph/车道 |

**一条只装到 45% 容量的路,不应该堵满 4 小时。** 差 2 倍,而 S3 拥堵支路误差只有约 20%,不是测量误差能解释的。

按走廊:I-66 WB 19 条,480 vph/车道(24% 容量),比值 **0.33**;I-395 SB 反而吻合(0.95)。

### 偏差 6:方案漏了一个原因

方案列了三类(network coding / volume-delay 标定 / OD),漏了对单 link 模型最要紧的:

**下游回溢** —— 一条 link 可以在自身需求远低于自身容量时排队,因为队列从下游堵回来。**这正是单 link 点队列模型无法表达的东西。** 是方法的固有边界,不是哪个输入错了。

## 第 6 步:跑队列

$$\text{out}(t)=\min\Big(\mu(t),\ \lambda(t)+\tfrac{Q(t)}{\Delta t}\Big)$$
$$Q(t+\Delta t)=\max\Big(0,\ Q(t)+\big[\lambda(t)-\text{out}(t)\big]\Delta t\Big)$$

一条连续递推,06:00 → 19:00,`Q(06:00) = 0`,周期边界不重置。

**23 条 link 在 15:00 时已带着队列进来** —— PM 单独跑会把它们扔掉。

### 上界在这里证明了自己

不削顶时,**4 条 link 的队列涨到存储量的 55 倍**,其中 **3 条实测队列是 0.0** —— 模型在速度显示畅通的地方凭空造出几千辆车。

这 4 条**正是第 5 步标记 `above_upper` 的那几条**,而且所有 `bins_pushed_over_mu > 0` 的 link 全部炸了。方案原话一字不差地发生了。

处理:**λ 在自由流 bin 上不得超过 μ_free**,削顶,把放不下的量报出来(5 条 link、60 个 bin、17,826 辆)。

| | 削顶前 | 削顶后 |
|---|---:|---:|
| 超存储量的 bin | 102 | **0** |
| 最差 峰值/存储 | 55.12 | **0.71** |
| 带进 PM 最大队列 | 10,076 辆 | 151 辆 |

### 结果

| | |
|---|---|
| 队列峰值 | 模型 43 辆 vs 目标 46,比值 0.962 |
| 残差 | 全程 RMSE 2.8 辆 |
| 19:00 仍有队列 | 33 条,中位 24 辆 |

19:00 的残留是**对的**:18:45 时仍有 28 条 link 观测速度低于 cutoff。窗口停在 19:00 只因为 assignment 没有 NT 期。

## 第 7 步:队列转回速度

$$TT(t)=\frac{L}{v_f}+\frac{Q(t)}{\mu(t)},\qquad \hat v(t)=\frac{L}{TT(t)}$$

**这一步不拟合任何东西。**

**和之前交付的那版的本质区别:** 那版把 t0、T2、t3、v_T2 从观测读出来再画 QVDF 碗,谷底必然吻合,P 和 v_T2 的"对比"是空的。这版把同一个检测器跑在 `v̂` 上,**P、T2、v_T2 是输出**。

| | |
|---|---|
| 模型 episode | **84 个,73 条 link**(PM 46 / AM 33 / MD 5) |
| `v̂` 等于 v_f 的 bin | **90.6%** |

`v̂ = v_f` 是因为 Q=0 时点队列没有延误。**模型对自由流速度变化没有任何表达能力**,所以只有 episode 内的对比有意义。

### 最重要的结果:消融实验

单看 2.06 mph 分不清是谁的功劳,所以加了两个基线:

| | |
|---|---:|
| **assignment 相对空模型的贡献** | **+0.00 mph** |
| **速度数据相对 assignment 的贡献** | **+29.66 mph** |

**assignment 一点忙没帮上:**

| | |
|---|---:|
| λ_flat / μ_free 中位 | **0.448** |
| λ > μ(有可能排队)的 link | **3 / 252** |
| assignment-only 速度 = 自由流的 PM bin | **97.7%** |

**静态分配的流量只有容量的 45%,在 249/252 条 link 上永远产生不了任何拥堵。**

这和第 5 步"53 条有队列的 link 里 34 条低于下界"是同一个信号。

### 必须说清楚的一句

**那 2.06 mph 全部来自速度数据,而速度数据在第 4 步就被拟合过了。**

T2 在 46 条里 **28 条完全命中**、v_T2 有 **37 条差不到 1 mph** —— 因为 λ 本来就是拟合来复现速度隐含队列的。

**当前形态下,模型是在复现观测速度,不是在预测它。** 不能把 2.06 mph 当精度报上去。

### 过程中修的两个 bug

两个都让结果显得比实际好:

1. **模型 P 被虚增最多 4.5 小时** —— 运行窗口停在 19:00,仍在进行的 episode 被截断到午夜。现在只在窗口内真正闭合的 15 个 episode 上比 P。
2. **assignment 变体实际是用 λ=0 跑的** —— 第 7 步输出没带 `V_assign_veh`,读到 NaN 后置零,所以它和空模型完全相同。现在从第 5 步的表取,取不到直接报错。

---

## 现在还剩什么

**第 9 步(敏感性)没做。** 该扫的两个轴:capacity(config 里已配 1200–2400)和 free speed 分位数(p85–p99,cutoff 移动 1.7–3.8 mph)。

**但比敏感性重要的是第 8 步那个结论。** 它说明当前这条链子:

- 速度数据 → 队列 → 速度,是**闭环**,不是预测
- assignment 在这个闭环里**没有起作用**,因为它的量太低

要让它变成真的预测,得让 assignment 的量能驱动队列。而现在 assignment 的量比速度数据显示的低 2 倍 —— **那个 gap 本身才是这项工作真正的发现。**
