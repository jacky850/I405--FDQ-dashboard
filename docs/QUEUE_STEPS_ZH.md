# 单 link 队列模型:我们做了哪些实验,结果是什么

这份文档写给完全不懂交通的人看。每个名词第一次出现时都会解释。

---

## 一、我们到底在解决什么问题

### 手上有什么

想象一条高速公路。我们想知道两件事:

1. **这条路上有多少车在跑?**(流量)
2. **车跑得多快?**(速度)

现实是:**我们只有速度,没有车的数量。**

速度是 INRIX 这家公司卖的数据 —— 他们从车载 GPS 收集,每 15 分钟给一个平均速度。至于这 15 分钟里到底过了多少辆车,没有人数过(除非路上装了检测器,而绝大多数路段没有)。

另一边,交通规划部门有一个**交通模型**(下文叫 "assignment",分配模型)。这个模型的工作是:根据人口、就业、出行调查,推算"早高峰从 A 区到 B 区有多少人开车",然后把这些车分配到路网上,得出**每条路上应该有多少车**。

所以现在有两个来源:

| 来源 | 给出什么 | 可信吗 |
|---|---|---|
| INRIX | 速度(实测) | 实测,可信 |
| assignment 模型 | 车辆数(推算) | 推算,待验证 |

### 想验证什么

**核心问题:如果我们相信 assignment 给的车辆数,把它喂进一个排队模型,算出来的速度,能不能对上 INRIX 实测的速度?**

如果能对上 —— 说明模型是对的,以后没有速度数据的地方也能用模型算速度。
如果对不上 —— 说明模型的车辆数有问题,而差多少、差在哪,就是这项工作的产出。

### 什么叫"排队模型"

拿收费站打比方。

- 有车不断开过来 —— 这个速率叫 **λ(lambda,到达率)**,单位"辆/小时"
- 收费站每小时最多能放过去一定数量的车 —— 这个上限叫 **μ(mu,服务率)**
- 如果 λ > μ,放不完的车就在后面**排队**
- 如果 λ < μ,来多少放多少,不排队

一段高速公路就是这样一个"收费站":路本身有个通行上限(容量),来的车超过这个上限就堵。

排队长度按这个规则一格一格往前推(每格 15 分钟):

```
这一格能放出去的车 = min( 服务率μ , 新来的车λ + 已经排着的车 )
下一格的队列 = 这一格的队列 + 新来的 − 放出去的   (不能为负)
```

这就是全部的模型。**我们要做的,是把 μ 和 λ 这两个数从数据里弄出来,然后跑这个递推,看算出的速度对不对。**

## 二、名词表

| 名词 | 意思 |
|---|---|
| **link** | 路网模型里的一小段路。assignment 模型的输出是按 link 给的 |
| **TMC** | INRIX 划分的路段编号。速度数据是按 TMC 给的。一个 TMC 通常覆盖几条 link |
| **free flow speed(自由流速度,v_f)** | 路上没车时能跑多快。**这个值极其关键**,后面单独讲 |
| **capacity(容量,C)** | 每条车道每小时最多能通过多少辆车。典型值 2000 |
| **cutoff(拥堵阈值)** | 速度掉到自由流的 70% 以下,就算这条路堵了 |
| **episode(拥堵事件)** | 一次连续的拥堵过程:从开始变慢,到最慢的那一刻,再到恢复 |
| **P** | 一次 episode 持续多久(小时) |
| **T2** | 一次 episode 里最慢的那个时刻 |
| **v(T2)** | 最慢时刻的速度 |
| **S3** | 一个公式,输入速度、输出流量。下面详细说 |
| **V_assign** | assignment 模型给出的、这条 link 在这个时段的总车辆数 |

## 三、我们用的数据

- **四条走廊**:I-395 北向/南向,I-66 东向/西向
- **252 条 link**,来自 **154 个 TMC**
- 速度:2025 年 10 月 **23 个工作日**的平均值,每 15 分钟一格
- assignment 输出:早高峰(AM)、平峰(MD)、晚高峰(PM)三个时段的车辆数

所有输入来自共享包 `link-queue-simulation`。代码在 `scripts/queue_step*.py`,输出在 `outputs/nvta_queue/`。

**一个必须先说清的事实:一个 TMC 会覆盖多条 link。**

| 一个 TMC 覆盖几条 link | 有多少个 TMC 这样 |
|---:|---:|
| 1 条 | 72 |
| 2 条 | 31 |
| 3–6 条 | 27 |
| 10 条 | 2 |

也就是说,**252 条 link 背后其实只有 154 个独立的速度观测**。同一个 TMC 下面的几条 link,速度完全一样。所以后面说"76 条 link 有拥堵"的时候,要记得真实的独立证据是 **44 个 TMC**,不是 76 个。汇报样本量时不能按 link 数报。

## 四、开工前的实验:自由流速度到底是多少

**为什么先做这个:** 自由流速度决定了 cutoff(70% 那条线),cutoff 决定了哪些时刻算"堵",哪些算"不堵"。这个判断错了,后面全错。

原来的做法是相信 assignment 模型里写的自由流速度。我们决定**自己从原始速度数据里算一遍**,用六种不同的口径:

| 走廊 | TMC 数 | **每个TMC取p95**<br>(最终采用) | 整条走廊取p95 | 夜间中位数 | 全天最高速 | INRIX自带参考值 | assignment写的 |
|---|---:|---:|---:|---:|---:|---:|---:|
| I-395 北 | 21 | **65.62** | 65.89 | 61.92 | 69.59 | 59.0 | 63.0 |
| I-395 南 | 20 | **63.18** | 64.77 | 59.57 | 68.50 | 59.5 | 63.0 |
| I-66 东 | 57 | **67.86** | 71.00 | 63.60 | 71.48 | 64.0 | **75.0** |
| I-66 西 | 56 | **67.88** | 70.93 | 64.52 | 72.00 | 64.0 | **75.0** |

("p95" = 把这段路全天所有速度排序,取第 95 个百分位,也就是"跑得比较顺的时候的速度",比取最高值稳健)

### 实验 1:assignment 的值可能吗?

有一条硬道理:**一条路的自由流速度,不可能高过这条路实际跑出过的最高速度。** 拿这条去查:

| 用哪个值 | 有多少 TMC 高过实测最高速 |
|---|---:|
| assignment 写的 | **72 / 154(47%)** |
| 我们算的每TMC p95 | 0 |

具体的例子:I-66 西向全部 109 条 link 都被赋了 75 mph,但其中 link 26304 **全天最高才 55.00 mph**。说它的自由流是 75,意味着它一天 24 小时永远在"堵",这显然不对。

### 实验 2:为什么不能用整条走廊一个值

同一条走廊里,不同路段的 p95 差了 **16–22 mph**。I-66 东向整体算出来 71.0,那是最快那几段的水平。把 71.0 套到一个自己 p95 只有 54.3 的路段上,cutoff 会差 11.7 mph —— 那一段就会被判成常年拥堵。

**所以必须每个 TMC 单独算。**

### 实验 3:我们算的值可信吗

拿两条独立的路径对照:

| 对照对象 | 相关系数 |
|---|---:|
| INRIX 自己给的 `reference_speed` | **0.963** |
| 夜间(00:00–05:00)实测中位数 | **0.979** |

高度一致,只差一个大约 3.7 mph 的常数偏移(合理 —— 夜间中位数本来就该比 p95 低一点)。分位数从 p95 换成 p85 或 p99,cutoff 只移动 1.7–3.8 mph,结论不敏感。

### 结果

换成我们自己算的自由流速度之后,原来那 12 个"全天 24 小时都在堵"的荒谬 episode,**自动消失了 9 个**,不需要写任何过滤规则。

## 五、第 1 步:从速度反推流量

### 想做什么

我们只有速度,但排队模型需要流量。**S3 公式**就是干这个的 —— 交通流理论里,速度和流量有固定的对应关系:

- 路上没车 → 速度快,但流量小(因为车少)
- 车适中 → 速度中等,流量最大
- 路上塞满 → 速度慢,流量也小(因为都动不了)

所以流量随速度先升后降,是个**倒 U 形**。S3 是这个倒 U 形的一个具体公式。

### 实验:检验实现对不对

S3 在数学上有个已知的性质:**流量最大的那一刻,速度应该正好是自由流的 0.707 倍**(√2 分之一)。我们跑完之后按速度分档统计:

| 速度 / 自由流速度 | 流量 / 容量(中位) |
|---|---:|
| 0.30–0.50 | 0.877 |
| 0.50–0.65 | 0.977 |
| **0.65–0.72** | **0.999** ← 峰值 |
| 0.72–0.85 | 0.975 |
| 0.85–1.10 | **0.826** |

峰值恰好落在 0.707,最大值 `q/C = 1.0000`。**实现正确。**

### 但有一个必须记住的副作用

看最后一行:一条**以自由流速度跑的空路**,S3 说它载着 **83% 的容量**。

这不是测量出来的,这是 S3 在高速段的固定返回值 —— 因为高速时速度对车辆数不敏感,轻微的速度差异对应巨大的流量差异,反推不出来。

PM 时段只有 **20.3%** 的时间格速度低于 cutoff。**也就是说,80% 的流量数字是不可信的。** 这个事实后面反复出现。

## 六、第 2 步:服务率 μ ——「这条路每小时最多能放多少车」

μ 有两个状态:

- **μ_free**:路还没堵的时候,最大放行率
- **μ_queued**:已经堵住之后,放行率会下降(这是真实现象,叫 "capacity drop",堵住之后车流断断续续,通过能力反而变差)

### 实验:μ_free 能测出来吗?

原计划是"从数据里测出 μ_free"。我们用同一个估计器,喂进五个不同的假设容量,看结果:

| 假设的容量 C | 算出的 μ_free / C |
|---:|---:|
| 1800 | 0.9979 |
| 2000 | 0.9979 |
| 2200 | 0.9979 |
| 2400 | 0.9979 |

**μ_free 永远等于你输入的 C 乘 0.998。一点信息都没有。**

### 为什么

这不是估计误差,是一个数学恒等式:

- S3 公式在速度 = 自由流 × **0.707** 时,流量**恰好等于容量 C**
- 我们的 cutoff 定在自由流 × **0.70**
- **这两个几乎是同一个点**

"崩溃前的最大流量"这个窗口必然扫过 0.707 那个点,必然取到 C。

真实数据佐证 —— link 25947 在 16:15 那一格:

| 时刻 | 速度 | 速度/自由流 | C设1800时的q | C设2000时的q | C设2200时的q |
|---|---:|---:|---:|---:|---:|
| 16:15 | 44.67 mph | 0.709 | **1800.0** | **2000.0** | **2200.0** |

一模一样,严丝合缝。

### 结论

**μ_free 是输入,不是测量结果。** 既然结果注定等于 C,就直接读配置里的 `link_capacity`,把那一堆检测代码删掉。

(顺带:原计划强调要"逐天估峰值再取中位数",实测这样做和"先平均再取峰"只差 **0.30%**,方向还相反。这套机器也删掉了。)

### 能测的只有比值

`capacity drop = 1 − μ_queued/μ_free`。这个式子里 C 上下约掉了(C=1900 和 C=2200 算出来差 3.3e-16,机器精度):

| | 中位数 | 四分位区间 |
|---|---:|---:|
| **实测 capacity drop** | **6.83%** | 3.71–10.90% |
| 原来配置里假设的 | 10% | |

**但严格说这也不是真测量。** 文献里的 capacity drop 是用路上的检测器数车得到的 —— 堵前堵后两个流量各自独立观测。我们这里两个数都是同一条速度曲线过同一个 S3 公式变出来的,不是独立证据。

### 顺手回答了一个问题:早高峰和晚高峰的 capacity drop 一样吗?

| | 样本数 | drop 中位 |
|---|---:|---:|
| 早高峰 | 34 | 3.99% |
| 晚高峰 | 47 | 8.67% |

统计检验 p = 0.030,看起来"显著不同"。**但这个结论站不住:** 早上堵的 link 和晚上堵的 link 基本是两批完全不同的路,这个差异里混着"哪些路容易堵"的成分,不是纯粹的时段效应。

同时有早高峰和晚高峰 episode 的只有 **7 条 link**。在这 7 条上,晚高峰减早高峰 = **−2.13 个百分点,方向反过来了**。

**结论:现有数据答不了这个问题。** 好在我们每个 episode 各存一个 μ_queued,不需要按时段合并,不影响后面。

### 异常 episode 怎么处理

有 12 个 episode 超过 8 小时,看着不正常。第一反应是按时长删掉,但检查后发现**不能删**:

- 时长和拥堵深度的相关性只有 0.22 —— 长不等于假
- 最长的那几条是 I-395 北向速度掉到 **9.4 mph** 的真拥堵,是全网最堵的证据

改用**深度门槛**(最慢速度要低于 cutoff 的 85%),滤掉 14 个又短又浅的噪声。

最终:**87 个 episode,分布在 76 条 link 上**(晚高峰 47 / 早高峰 34 / 平峰 6),没有一个 capacity drop 为负。

### 一个记下来但没处理的发现

如果**不看阈值**,直接找速度掉得最猛的那一刻(真正的"崩溃点"),它落在自由流的 **0.82 倍**,不是 S3 说的 0.707。**72% 的 link 在 S3 认为的最大流量速度之上就已经崩了**,中位差 10.6 mph。

按这个反推,S3 的形状参数 m 应该是 7 而不是 4。第 3 步查了这个偏差的影响,很小(见下),所以没改。

## 七、第 3 步:速度告诉我们队列有多长

### 想做什么

这一步是整个链条的枢纽:**把"速度"翻译成"排了多少辆车"**,作为后面拟合的靶子。

逻辑很直接:

```
自由流时开完这段路要多久 = 路长 / 自由流速度
实际开完要多久           = 路长 / 实际速度
多花的时间               = 两者之差 = 被队列耽误的时间
排了多少辆车             = 耽误的时间 × 每小时放行率μ
```

单位对得上:小时 × 辆/小时 = 辆。

用的是**未平滑**的速度 —— 平滑过的版本已经用来定 episode 和 μ 了,再用一次等于把同一次平滑洗两遍。

### 结果

| | |
|---|---|
| 有队列的 link | 76 条(44 个独立 TMC) |
| 峰值队列 | 中位 **46 辆**,四分位 29–78,最大 326 |
| **物理检验:队列超过路能装下的车数了吗** | **0 个时间格超标**,最差 0.74 |

最后一行是个重要的自查:一段 1 英里 3 车道的路最多能塞下大约 600 辆车。如果算出来的队列比这还长,说明公式错了。**没有一次超标。**

### 实验:episode 的边界是不是切掉了真队列

第 2 步发现崩溃点在 0.82 而我们的 cutoff 在 0.70,中间那段被判成"不堵",队列被清零了。会不会丢掉很多?

我们只在 episode 内保留队列,episode 外清零。统计被清掉的量:

| | |
|---|---:|
| episode 外被清零的总量 | 54.5% |
| 但**每个时间格**平均:episode 内 vs 外 | 43.5 辆 vs **3.11 辆** |
| 时间格数量比 | 外 : 内 = **16.7 : 1** |
| 被清掉的量里,发生在**从来不堵**的 link 上的 | 65% |
| **真正被误切的,相对捕获量** | **6.5%** |

**54.5% 是统计假象。** 它大只是因为 episode 外的时间格实在太多了(16.7 倍),每格才 3.11 辆。

那 3.11 辆是**口径本身的地板**:自由流速度取的是 p95,意味着 95% 的时间格速度都略低于它,`路长/实际速度 − 路长/自由流速度` 永远是个小正数。**那不是队列,是定义带来的常数残差。**

**结论:cutoff 定在 0.70 偏保守,代价是 6.5%,不值得为此改动。**

## 八、第 4 步:到达率 λ ——「每小时有多少车开进来」

### 想做什么

μ 有了,队列的观测值也有了。反过来解 λ:

```
队列的变化速度 = 进来的 − 出去的
所以  λ = μ + 队列的变化率
```

最直接的做法是逐点差分:每一格用队列的差值直接算 λ。全天 96 格,就得到 96 个 λ 值。

我们没这么做,而是改用 **27 个 B-spline 系数**(每 60 分钟一个节点)去拟合这 96 格。B-spline 你可以理解成"用 27 个旋钮控制一条光滑曲线的形状"。

### 实验 1:为什么不逐点差分?原计划给的理由对吗

原计划说逐点差分会被噪声淹没(说会放大 12 倍)。我们实测:

| | 逐点差分 | B-spline |
|---|---:|---:|
| 相邻格之间的跳动(标准差) | 23 vph | 17 vph |
| 占 μ 的比例 | 0.33% | 0.25% |
| 出现"负到达率"(物理不可能)的 link | **0 / 76** | 0 |

**只噪 1.3 倍,不是 12 倍。原计划的理由不成立。**

原因是我们的数据比原计划假设的干净大约 6 倍:时间格从 5 分钟变成 15 分钟(差分放大小 3 倍),天数从 5 天变成 23 天(平均后噪声小 2.1 倍)。

### 实验 2:那为什么还是要用 spline?

真正的理由完全不同,而且更重要。

**实验:把 96 个自由的逐点 λ 喂进递推,看能拟合得多好。**

```
残差 RMSE = 0.000 辆 = 峰值的 0.000%
```

**完美复现 —— 而这正是问题所在。** 96 个观测、96 个未知数,方程组恰定,残差**必然**为零。这样的模型**永远不可能失败**,所以它什么也没证明。

**实验:改变节点间距,看参数少了会怎样。**

| 节点间距 | 系数个数 | 每个系数管几格 | 残差 RMSE | 占峰值 |
|---:|---:|---:|---:|---:|
| 15 分钟 | 99 | 0.97 | — | 求解器直接拒绝(参数比数据还多) |
| 20 分钟 | 75 | 1.3 | 2.88 | 2.2% |
| **60 分钟** | **27** | **3.6** | 5.50 | **4.1%** |
| 480 分钟 | 6 | 16.0 | 10.94 | 8.5% |

**参数越少,残差越大 —— 这正是我们要的。** 只有当参数少于数据时,"拟合得好"才是个真信息。

**那 4.1% 的残差是买"可证伪性"付的钱。** 想让残差数字好看,只要把节点调密就行 —— 但那样第 8 步的验证就变成自说自话了。

### 结果

| | |
|---|---|
| 拟合的 link | 76 条 |
| 队列残差 | RMSE 中位 2.0 辆,占峰值 **4.1%** |
| 拟合峰值 / 实测峰值 | 0.968 |
| 相关性 | **0.9842**(逐 link 取中位是 0.944) |
| λ 无负值、队列无负值、所有 link 当天清零 | 全部通过 |

物理上也对:λ 在 μ 上方时队列涨,在下方时队列落。双峰的 link 两个峰都跟上了。

### 一个结构性的发现:94% 的时间 λ 根本解不出来

**λ 只在 5.6% 的时间格上可识别。**

原因很朴素:剩下 94.4% 的时间没有队列。**没有队列的时候,`队列 ≡ 0` 对任何小于 μ 的 λ 都成立。** λ = 800、1500、1999,给出的队列和速度**完全相同**。

这不是"估不准",是**数学上没有唯一解**。这 94.4% 的时间格必须靠别的信息来定 —— 那就是第 5 步。

## 九、第 5 步:用 assignment 的总量来定剩下的 94%

### 想做什么

第 4 步解不出来的那 94% 的 λ,用 assignment 模型的总量来定:

```
一个时段内所有 λ 加起来 × 时长 = assignment 给的这个时段总车辆数
```

**先验证单位。** 这个项目早先在单位上栽过一次,所以这回先查:`D = volume / (车道数 × 时段小时数 × plf)` 这个关系在 **100% 的行**上成立,误差 <0.1%。确认 `volume` 是**这个时段全部车道的总车辆数**。

三个时段(早高峰、平峰、晚高峰)都跑,因为第 6 步是一条从早到晚不间断的递推,15:00 时已经排着的队必须带进晚高峰。

### φ:怎么在时段内分配

有了时段总量,怎么分到每一格?原计划用 **φ(phi)** —— 把 S3 算出的流量形状归一化,按这个形状分。

**但我们发现整个时段用 φ 是错的:堵的时候,S3 算出的流量是"通过量"不是"需求量"。**

堵得最狠那一刻,需求最高,但因为车都动不了,通过的车反而最少。所以整个时段用 φ 会**把需求高峰压成一个凹坑,形状完全反了**。

所以改成:

| 时间格类型 | λ 从哪来 |
|---|---|
| 有队列的(5.6%) | 第 4 步的队列拟合 |
| 自由流的(94.4%) | **φ,但只在自由流的格子上归一化** |

实测 φ 在自由流段几乎是平的(0.097–0.102),因为 S3 在高速时对速度不敏感。**所以 φ 其实没带来多少形状信息,基本等于平均分配。**

### 实验:assignment 的总量合理吗

我们造了两个**完全不依赖 assignment** 的边界:

- **下界** = 拥堵时段实际疏散掉的车 = 我们已经亲眼看到通过的量。assignment 不可能比这还少。
- **上界** = 下界 + 自由流时段按最大放行率能装下的量。assignment 不可能比这还多。

结果:

| 时段 | 总 link | 落在上下界内 | 有队列的 link | 其中落在界内 | **其中低于下界** |
|---|---:|---:|---:|---:|---:|
| 早高峰 | 252 | 226 | 37 | 13 | **22** |
| 平峰 | 252 | 239 | 49 | **36** | 12 |
| 晚高峰 | 252 | 213 | 53 | 15 | **34** |

**平峰基本吻合,早晚高峰对不上。**

看晚高峰那 34 条对不上的 link 具体是什么情况:

| | 中位数 |
|---|---:|
| assignment 说这条路上有多少车 | **903 辆/小时/车道** |
| 占容量的比例 | **45%** |
| 但速度数据显示它排队排了多久 | **4.00 小时** |
| 排队期间实际的疏散速率 | 1,677 辆/小时/车道 |

**一条只装到 45% 容量的路,不应该堵满 4 个小时。**

差了整整 2 倍。而 S3 在拥堵段的误差只有大约 20%,**这不是测量误差能解释的**。

按走廊拆:I-66 西向有 19 条,只给了 480 辆/小时/车道(24% 容量),比值 **0.33** —— 差了 3 倍。而 I-395 南向反而吻合得很好(0.95)。

### 这个差距可能来自哪

原计划列了三类原因(路网编码、拥堵函数标定、OD 需求),但漏了对单 link 模型最要紧的一类:

**下游回溢。** 一条路可以在自身车流量远低于自身容量时排队 —— 因为前面路口/瓶颈堵住了,队列一路倒回来。

**这正是单 link 点队列模型结构上无法表达的东西。** 它是方法的固有边界,不是哪个输入填错了。

---

## 十、第 6 步:跑队列

μ 和 λ 都有了,开始跑递推:

```
这一格放出去 = min( μ , λ + 已排着的车/时长 )
下一格队列   = max( 0 , 这一格队列 + λ − 放出去的 )
```

**一条连续的递推,06:00 跑到 19:00,起点队列 = 0,时段边界不重置。**

不重置很重要:**有 23 条 link 在 15:00 时已经带着队列进入晚高峰。** 如果只跑晚高峰、从空路开始,这些车就被凭空扔掉了。

### 实验:上界真的有用吗

第 5 步造的那个上界,一开始只是个诊断指标。我们先**不做任何削顶**跑一遍:

**4 条 link 的队列涨到了路能装下车数的 55 倍** —— 其中 **3 条实测队列是 0.0**。也就是说,模型在速度显示完全畅通的路上,凭空造出了几千辆车。

关键是:**这 4 条正是第 5 步标记为"超过上界"的那几条。** 而且所有"λ 被推到 μ 以上"的 link 全部炸了,一条不漏。上界这个诊断指标精确地预言了哪些 link 会失控。

处理办法:**自由流的格子上,λ 不允许超过 μ_free**,超出的削掉,并把放不下的量如实报出来(5 条 link、60 个时间格、17,826 辆车)。

| | 削顶前 | 削顶后 |
|---|---:|---:|
| 队列超过路容量的时间格 | 102 | **0** |
| 最差的 峰值/容量 | 55.12 | **0.71** |
| 带进晚高峰的最大队列 | 10,076 辆 | 151 辆 |

### 结果

| | |
|---|---|
| 队列峰值 | 模型 43 辆 vs 目标 46 辆,比值 **0.962** |
| 全程残差 | RMSE 2.8 辆 |
| 19:00 还有队列没清完的 link | 33 条,中位 24 辆 |

最后一行**是对的,不是 bug**:18:45 时仍有 28 条 link 的**观测速度**低于 cutoff,路上确实还堵着。窗口停在 19:00 只是因为 assignment 没有夜间时段的数据。

---

## 十一、第 7 步:把队列换算回速度

```
开完这段路的时间 = 路长/自由流速度 + 队列长度/放行率μ
模型速度         = 路长 / 这个时间
```

**这一步不拟合任何东西。** 队列来自第 6 步,μ 来自第 2 步,只有上面这个算术。

### 这一版和之前交付给导师那一版的本质区别

之前那一版:把 t0、T2、t3、v(T2) 从**观测里直接读出来**,再画一条 QVDF 曲线穿过这些点。谷底必然吻合,所以"P 和 v(T2) 的对比"是空的 —— 拿观测值和它自己比。

**这一版:P、T2、v(T2) 是输出。** 我们把第 2 步用过的同一个 episode 检测器,原封不动地跑在模型速度上,让它自己找出拥堵什么时候开始、什么时候最慢、最慢多少。然后才拿去和观测比。

**这才是真比较。**

| | |
|---|---|
| 模型自己检测出的 episode | **84 个,73 条 link**(晚高峰 46 / 早高峰 33 / 平峰 5) |
| 模型速度恰好等于自由流的时间格 | **90.6%** |

最后一行是结构性的:队列 = 0 时点队列模型没有任何延误,所以模型速度就是自由流。**模型对"自由流时速度的正常波动"没有任何表达能力。** 因此只有 episode 内部的对比有意义。

---

## 十二、第 8 步:验证 —— 这是全文最重要的部分

### 速度对比(晚高峰)

MAE = 平均绝对误差,单位 mph,越小越好。

| 模型变体 | 整个晚高峰的 MAE | **拥堵期间的 MAE** | 偏差 |
|---|---:|---:|---:|
| free_flow(空模型:假装永远不堵) | 6.70 | 31.72 | +33.23 |
| **assignment 单独**(只用模型车辆数) | 6.70 | 31.72 | +31.12 |
| **anchored(我们交付的模型)** | **4.84** | **2.06** | **+0.17** |

拥堵期间 2.06 mph 的误差,看起来非常好。

### P、v(T2)、T2 对比

| 量 | 样本数 | 中位误差 | MAE |
|---|---:|---:|---:|
| **P**(拥堵持续多久) | 15 | −0.51 小时 | 0.51 小时 |
| **T2**(最慢的时刻) | 46 | **+0.00 分钟** | 0.00 |
| **v(T2)**(最慢时的速度) | 46 | −0.09 mph | **0.35 mph** |

episode 检测本身:观测到 47 个,模型产出 46 个,**匹配上 46 个(漏了 1 个,一个虚报都没有)**。

### 关键实验:消融 —— 这 2.06 mph 到底是谁的功劳

**光看 2.06 mph 分不清是模型好还是数据泄漏。** 所以我们加了两个基线,跑完全一样的递推、完全一样的速度换算,只换 λ 的来源:

| 基线 | λ 从哪来 |
|---|---|
| **free_flow** | λ 低到永远不排队。这是"空模型",什么信息都没用 |
| **assignment** | λ = assignment 的总量 / 时段长度,时段内平均分配。**完全不用速度数据** |
| **anchored** | 交付的模型:有队列的地方用第 4 步拟合,没队列的地方用 assignment 定 |

结果:

| | 拥堵期 MAE 的改善 |
|---|---:|
| **assignment 相对于空模型的贡献** | **+0.00 mph** |
| **速度数据相对于 assignment 的贡献** | **+29.66 mph** |

**assignment 一点忙都没帮上。** 为什么:

| | |
|---|---:|
| assignment 的 λ / μ 中位数 | **0.448** |
| λ 有可能超过 μ(也就是有可能排队)的 link | **3 / 252** |
| assignment-only 模型速度等于自由流的晚高峰时间格 | **97.7%** |

**assignment 给的车流量只有容量的 45%,在 249/252 条 link 上永远产生不了任何拥堵。**

这和第 5 步"53 条有队列的 link 里 34 条低于下界"是**同一个信号的两种测法**。

### 必须说清楚的一句话

**那 2.06 mph 全部来自速度数据,而速度数据在第 4 步就已经被用来拟合了。**

T2 在 46 条里 **28 条完全命中**、v(T2) 有 **37 条误差不到 1 mph** —— 这不是巧合,因为 λ 本来就是拟合出来复现"速度隐含队列"的。

**当前形态下,这条链子是:速度 → 队列 → 速度。它在复现观测,不是在预测。** 不能把 2.06 mph 当作预测精度报出去。

### 过程中修的两个 bug(两个都让结果显得比实际好)

1. **模型的 P 被虚增了最多 4.5 小时。** 运行窗口停在 19:00,那时还在进行的 episode 找不到恢复点,被截断记到午夜。修法:只在窗口内真正结束的 15 个 episode 上比 P(所以 P 的样本数从 46 掉到 15)。

2. **assignment 这个基线实际是用 λ=0 跑的。** 第 7 步的输出没带 `V_assign_veh` 这一列,代码读不到就置零,所以这个基线和空模型完全相同 —— 我一度据此说"assignment 产生不了拥堵",那个结论当时是建立在 bug 上的。修法:改从第 5 步的表里取,取不到就直接报错退出。修完重新验证,结论仍然成立(λ/μ = 0.448)。

---

## 十三、总结:我们学到了什么

### 三个技术结论

1. **μ_free 在这套数据上测不出来。** 它恒等于输入的容量,因为 S3 的最大流量速度(0.707)和我们的拥堵阈值(0.70)几乎重合。它是输入,不是测量。

2. **λ 在 94% 的时间上没有唯一解。** 没有队列的时候,任何小于 μ 的 λ 都给出相同的观测结果。这不是精度问题,是结构问题。

3. **自由流速度必须每个 TMC 单独算。** assignment 给的值在 47% 的路段上物理不可能;整条走廊一个值会在内部差 16–22 mph。

### 一个方法论结论

**当前这条链子是闭环,不是预测:**

```
观测速度 → 队列 → 拟合 λ → 跑递推 → 队列 → 模型速度 → 和观测速度比
   ↑                                                          |
   └──────────────── 同一份数据 ─────────────────────────────┘
```

2.06 mph 是这个闭环的自洽度,不是预测能力。要变成真正的预测,必须让 assignment 的车流量能自己驱动队列。

### 最重要的一个发现

**assignment 给的车流量,比速度数据显示的疏散量低了 2 倍。**

- 在有队列的 53 条晚高峰 link 上,34 条的 assignment 量低于"我们已经亲眼看到通过了这么多车"的硬下界
- assignment 的 λ/μ 中位数只有 0.448,在 249/252 条 link 上永远堵不起来
- 而实测这些路堵了 4 个小时

**这个 2 倍的差距,本身才是这项工作真正的产出。** 它不是模型的失败,它是一个可以量化、可以按走廊拆解(I-66 西向差 3 倍,I-395 南向基本吻合)的诊断结果。

### 还没做的

**第 9 步(敏感性分析)。** 该扫两个轴:容量(配置里已经准备了 1200–2400)和自由流速度的分位数(p85–p99,cutoff 移动 1.7–3.8 mph)。优先级低于上面那个 2 倍差距的追查。
